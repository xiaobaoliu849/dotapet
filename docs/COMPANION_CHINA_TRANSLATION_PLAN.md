# DOTA2 桌面宠物：国内使用与聊天识别路线

更新：2026-10-08。这里区分 0.1.1 已实现的功能与下一阶段建议，不把接口测试当成实战效果测试。

## 产品定位与设置

桌宠的核心场景是 DOTA2 英雄 / 信使陪伴、看懂队友聊天、辅助自己用英文沟通。对话语气可以亲切，但名称与引导应明确写「DOTA2 桌面宠物」。避免先要求用户理解多个服务商、模型名、实时会话、OCR 等技术概念。

0.1.1 设置先问用途，再让用户选择服务商和粘贴密钥：

| 用途 | 国内选择 | 实际使用 |
|---|---|---|
| 文字与聊天截图翻译 | 千问、DeepSeek | 保存并测试文字模型，然后按 Alt+T；无需连接语音、无需开麦 |
| 与桌宠语音对话 | 千问、豆包 | 保存并测试语音、连接，再按 Alt+Q 开关麦克风 |
| 海外语音体验 | Gemini、Cartesia | 更多设置中主动显示；需相应账户、地区与网络条件 |

千问适合希望只配置一家服务的用户，但文字、视觉、语音实际使用不同模型，账户需要具备对应权限。DeepSeek 适合文字与图片翻译。多模态图片理解与实时音频会话是不同能力，不能因此把 DeepSeek 放进当前实时语音服务列表。

当前需要用户提供自己的 API Key。进一步面向完全不懂 API 的用户，应添加服务商官方开通引导和费用说明。若要实现用户登录即可用，需另建服务端鉴权、额度、计费和滥用限制；不能把开发者密钥放进安装包。

## 已核对的接口事实

- 本程序原有文字翻译已走千问 / DeepSeek，并不依赖 Google 翻译。语音列表中的「Google 实时翻译」是 Gemini 的实时语音模式，不能与所有文字翻译混为一谈。
- Google 官方支持地区列表没有中国大陆，因此大陆体验版不应把 Gemini 作为默认路径：[官方支持地区](https://ai.google.dev/gemini-api/docs/available-regions)。
- DeepSeek 官方明确 `deepseek-flash` 支持图片与文本输入，使用兼容 Chat Completions 的 `image_url` 内容块；它确实可以读取聊天截图：[Vision 文档](https://api-docs.deepseek.com/guides/vision/)。
- 千问视觉接口也支持图片输入，`qwen3-vl-flash` 支持关闭思考：[视觉理解文档](https://help.aliyun.com/zh/model-studio/vision)。地区、工作空间与 API Key 必须对应：[获取密钥](https://help.aliyun.com/zh/model-studio/get-api-key)。

0.1.1 采用这两家的视觉模型，短消息翻译关闭思考过程。网络、视觉编码与输出仍然需要时间；没有实测前不宣称「秒回」或固定延迟。

## 当前能操作的流程

按 Win+Shift+S 只框选可见聊天 → 剪贴板保存截图 → Alt+T → 所选视觉模型读取并翻译 → 桌宠浮层显示原文和中文。

这条路径不需要切到桌宠、粘贴截图、再点击提交。截图不会自动输入或发送到游戏，失败时不会调用其他服务商或假装识别成功。程序限制图片大小，并将超过 2048 像素的最长边缩小。不要截图整个画面：模型本身也可能缩放图片，整屏的小聊天字更容易丢失细节。

F8 是另一条路径：捕获自己聊天输入框中的文本、翻成英文、填回输入框，玩家检查后按 Enter。它不能读取别人发来的消息。已有 GSI 实现提供英雄、地图和玩家状态，没有聊天消息处理；不能把 GSI 当成现成聊天文本接口。

## 下一步：一次框定，一个快捷键

先新增「设定聊天区域」：用户在实际游戏画面框定一次，保存游戏窗口相对坐标。之后按一个快捷键直接捕获该区域并翻译，减少每次手动框选的步骤。显示模式、窗口大小、显示器或 DPI 改变时提示重新校准；前台不是 DOTA2 时不自动截图。

用户只需要看到三个操作：「设置聊天区域」「翻译当前聊天」「暂停自动翻译」。OCR 引擎、阈值和模型细节可以放在诊断信息中。

## 自动识别优先采用本地 OCR 加文字翻译

建议管线：

1. 仅游戏前台且用户启用时，采集小块聊天区域；首先验证无边框模式，再验证独占全屏的捕获效果。
2. 本机进行区域变化检测，画面没有相关变化时不 OCR、不请求云端。透明背景会随游戏变化，不能仅以整块像素哈希判定新消息，需要文字行级稳定性判断。
3. 本地 OCR 读取玩家名、队伍 / 全体标记和消息；为透明背景、描边字、不同字号测试预处理策略。可评估系统 OCR 与 PaddleOCR，先用实际截图测准确率、耗时和安装包体积再选型。
4. 通过位置、行序与近期文本序列跟踪新增消息。折行需要合并，聊天向上滚动不能重新翻译全部历史；不能永久按内容去重，因为同一个人可能再次发送相同战术。
5. 先查 DOTA2 术语和高频短句缓存，必要时调用国内文字模型，仅发送新增聊天文本；保留原文、玩家名和频道便于核对。
6. 不抢焦点地显示结果；自动翻译默认静音。屏幕识别不确定时显示「未识别清楚」，由用户手动触发视觉模型重试。

这条路线预计比持续向视觉模型发送整屏更适合比赛中使用：少传图片、减少重复请求、可独立改善 OCR。是否更快、是否足够准确，仍需基准测试，不把设计推测写成已验证结论。

## 其他获取消息的办法

| 路线 | 判断 |
|---|---|
| 手动聊天区域截图 + 多模态 | 已实现调用和错误处理；适合按需使用，仍需真实云端和游戏验收 |
| 固定聊天区域 + 本地 OCR + 国内文字翻译 | 推荐下一阶段，逐步实现手动单键与自动增量识别 |
| 游戏控制台 / 日志解析 | 只有确认当前客户端实际输出完整聊天、格式稳定、开启步骤可接受后，才作为可选实验；不能假设一定有日志 |
| 当前 GSI | 继续用于游戏状态与英雄联动；现有实现不能直接读取聊天 |
| 队友语音翻译 | 需要单独捕获游戏音频并做语音识别 / 翻译；桌宠麦克风输入不等于队友语音 |

## 体验版验收与实战验收

已实现的自动测试验证服务商选择、图片请求结构、关闭思考、缺密钥拒绝、失败无虚构译文、截图优先于旧文本、尺寸限制，以及截图流程不输入游戏、不覆盖剪贴板。桌面冒烟测试验证首次引导、国内用途选择、加密保存、界面缩窄和本机麦克风检查收尾。

实战验收另需收集获准使用的聊天样本，覆盖英文 / 西里尔字母 / 中英混合、rosh / ss / bkb 等缩写、相同重复消息、多行折行、滚动、聊天透明度和不同 DPI。分别记录捕获、OCR、云端和浮层显示耗时，统计 P50 / P95、新消息召回率、重复展示率与术语正确率，并观察游戏帧率影响。当前未用真实账户测在线识别准确率和延迟。

版本路线：0.1 先解决名称、用途设置、国内模型与手动截图；下一版优先固定区域的单键翻译；随后加入默认关闭的自动 OCR 增量识别，实测达标后再考虑更广泛发布。
